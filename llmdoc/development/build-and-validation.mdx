# 构建产物与验收边界

仓库维护 JS SDK、浏览器扩展与 Codex/Claude Code 插件。命令和版本以 manifest、构建脚本及 README 为准；这里维护构建顺序、产物权属和验收边界。Python/Go SDK 及其 ZIP 副本、专属检查不再属于构建链。

## 选择并完成同一种构建

普通安装通过 `prepare` 构建 JS 包和扩展，不要新增再次调用安装的 `install` 生命周期入口。普通构建不重新生成协议，也不代表已构建插件。

ReverseWS 与 NATS 是资源编译时开关，普通 `build` 会关闭。已有浏览器启动入口必须先完成普通构建，再以 ReverseWS 开关重建扩展，最后直接执行代理 CLI；再次调用普通构建会覆盖开关。Paseo 快捷入口应复用根脚本。

扩展资源构建同时产生可加载目录和归档。构建不是事务：失败后应重新完成整条链，不能分发新旧混合产物；跨平台归档字节不保证完全相同。浏览器须加载对应产物目录，重建不 watch、不自动重载，也不更新另一 worktree 装载的扩展。

## 插件是完整可搬运的产物

插件构建生成 `dist/plugin-marketplace`，提供 Codex 与 Claude Code 的 marketplace/plugin 配置、技能、入口和生产运行依赖；浏览器扩展为独立 Release ZIP，由用户自行下载并手动加载。构建端解析依赖闭包并物化文件，客户端不依赖源码 checkout、pnpm 符号链接或安装脚本，也不下载 Playwright 浏览器。插件不能接收扩展目录或下载、复制扩展来配置实例。

插件使用的扩展以 ReverseWS 构建；普通构建不能替代该步骤。入口校验随包文件并运行完整产物，不通过下载或缓存复制修补依赖；客户端只使用用户提供的 Node ≥ 22，不自动切换 Node 或修改 PATH。依赖、版本或入口变化时应重建完整插件，不能单独替换已校验文件。profile 的连接身份位于扩展 storage，公共扩展目录不是实例配置写入点。

唯一插件分发入口为 cdpHelper 的 main 分支：该仓根维护两端 marketplace，`plugins/cdphelper` 放完整产物，不引入或复制 ModCDP 源码。ModCDP 维护源码、构建和测试，并从根目录 `cdpHelper/` 子模块锁定分发仓提交；初始化后可在当前源码工作区看到市场与插件。关联方向只能是 ModCDP → cdpHelper，不能在分发仓反向建立 `source/ModCDP` 子模块或形成递归引用。扩展 ZIP 独立放 cdpHelper Release，不进入插件目录或插件 Git 树，不使用 plugin-dist 分支。仓库不通过 npm 分发本插件。

交付顺序为：提交干净源码 A，从 A 构建并记录真实 source_commit；在 cdpHelper 核验、提交产物 B；最后由 ModCDP 的后续提交 C 将子模块锁定 B。C 只更新分发关联时，产物来源仍是 A，不能为了让来源等于父仓最新 HEAD 反复重建而制造循环引用。更新产物、父仓指针与 Release 附件是不同交付步骤；构建成功不等于它们已发布或验收。对外分发前，来源 A 与分发 B 都须能从各自配置的远端取得，本地对象可用不证明远端可用。

父仓的格式化、检查与构建工具不得递归改写子模块内已校验的产物或其生产依赖；子模块内容由分发仓独立维护、提交和核验。不能用修改父仓忽略规则来替代检查子模块本身的 Git 状态。

构建器从 skills/cdphelper 生成插件技能，以 --cdphelper-plugin 编译配套扩展；扩展 ZIP 命名为 cdphelper-extension-v版本号.zip，构建来源记录在扩展内的 cdphelper-bridge.json。版本与摘要以构建元数据为准。改名不更换扩展公钥或 ID，也不改变 bridge 协议；插件和配套扩展仍须按构建版本匹配。

## 验证到所需责任边界

静态检查、自动化协议/插件测试、真实宿主加载、独立测试浏览器和真实雪诺是不同验收范围。端口可访问只证明入口存在；页面操作还须越过扩展登记、调试权限和目标会话边界。reuse 与 isolated 均须按所选 profile 完成真实页面验收，不能以其中一种成功替代另一种。旧的专属目录/动态端口测试成功不能直接证明新的统一登记契约通过；SDK 直连也不能证明宿主解析清单正确。父仓子模块的 URL、gitlink 与实际检出一致，分发仓没有反向源码子模块，产物来源准确，main 市场安装和 Release 附件完整性，均须分别验收，不提前宣称通过。

完整测试可能依赖外部服务和固定资源；本地执行应避免端口、浏览器和前端连接冲突。保留正常 hooks；未安装 hook 时明确实际执行的手动检查。报告分别说明构建、自动回归、真实浏览器操作及尚未满足的外部前提。

首次安装验收须使用空运行时目录和宿主默认连接时限，确认冷启动成功后再单独验证缓存复用；不能以已预热目录的连接成功代替首次使用验收。

用户明确要求替换全局插件时，先备份相关注册、市场来源及工具审批设置，再用独立宿主配置安装和校验候选，之后通过宿主管理命令替换用户级插件。Codex 的工具审批需迁移到新插件和 MCP 命名空间，其他插件配置及活动浏览器不受清理授权。安装缓存摘要、技能加载和 MCP 连通要分别核验；不手工覆盖缓存，也不以临时宿主测试代替真实用户级安装结果。
